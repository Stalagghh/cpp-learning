# День 7 — Проект и разбор недели

> [!abstract] О чём эта лекция
> Новых конструкций языка сегодня нет ни одной: типы, ветвления, циклы, вложенные циклы и массивы это уже всё, что нужно. Новое другое: как собрать из них программу, которая больше одной задачи и не рассыпается на середине. Вторая половина дня уходит на разбор: перечитать свой код первого дня, завести файл ошибок и посмотреть, что за неделю реально встало в руки.

---

## 1. Чем проект отличается от задачи

Ты решил около сотни задач. Устроены они все одинаково: получил данные, посчитал, напечатал ответ, программа закончилась. Проект работает иначе.

| | Задача | Проект |
|---|---|---|
| Сколько раз что-то делает | один раз | сколько захочет пользователь |
| Данные | пришли, посчитались, забылись | живут между действиями |
| Путей исполнения | один | столько, сколько пунктов меню |
| Неверный ввод | его не бывает, судья подаёт корректный | норма жизни, программа обязана его переживать |
| Где помещается | целиком в голове | не помещается, нужен план на бумаге |

Главное слово тут «состояние». В задаче переменная нужна на пять строк. В проекте массив с историей операций должен пережить двадцать нажатий и остаться правильным. Отсюда и все сегодняшние трудности.

---

## 2. Выбор проекта

Один из четырёх. Выбирай и не меняй на середине: смена проекта на половине пути это способ не закончить ни один.

| Проект | Что тренирует | Где будет трудно |
|---|---|---|
| Угадайка с уровнями сложности и подсчётом попыток | случайные числа, вложенные циклы, подсчёт статистики | посчитать средние попытки по нескольким партиям |
| Калькулятор с меню и историей операций | массив как хранилище, `switch`, деление на ноль | хранить историю (что именно хранить: результат, или всю операцию) |
| Быки и коровы | логика сравнения, вложенные циклы, разбор числа на цифры | сам подсчёт быков и коров, там легко ошибиться на повторах |
| Журнал оценок | массив, поиск максимума и минимума, среднее, подсчёт по условию | ничего сложного, зато закрепляет вчерашнюю тему целиком |

Если вчерашние массивы дались тяжело, бери журнал оценок или калькулятор с историей. Если хочется помучиться над логикой, бери быков и коров: он честно сложнее остальных трёх.

Требования одинаковые для всех вариантов: меню, циклы, условия, массив, обработка неверного ввода. Объём 100-150 строк.

## 3. Начинай не с кода, а с трёх пунктов на бумаге

Пятнадцать минут на бумаге экономят полтора часа за клавиатурой. Три пункта, по порядку.

**Пункт 1. Одно предложение: что программа делает.** Именно одно. Если не влезает, значит ты собрался писать два проекта.

> Калькулятор с меню: считает четыре арифметические операции, запоминает результаты и умеет показать историю и среднее.

**Пункт 2. Список действий пользователя.** Это и есть твоё меню, слово в слово.

```
1 - посчитать
2 - показать историю
3 - среднее по истории
4 - очистить историю
0 - выход
```

**Пункт 3. Список данных, которые должны жить между действиями.** Самый важный пункт и единственный неочевидный.

```
history[MAX]   результаты операций
n              сколько результатов уже есть
```

Всё, что в этом списке, объявляется **до** главного цикла. Всё остальное (введённые числа, выбор пункта, счётчики) живёт внутри и спокойно пересоздаётся каждый проход.

> [!important] Правило
> Пока третий пункт не выписан, не начинай печатать. Именно из-за него потом переписывают половину программы: человек обнаруживает на семидесятой строке, что историю негде хранить, потому что массив объявлен внутри цикла и обнуляется на каждом проходе.

## 4. Каркас: то же меню из Дня 4, теперь как основа всего

```cpp
#include <iostream>

int main() {
    const int MAX = 100;      // физический размер
    double history[MAX];
    int n = 0;                // логический размер, из Дня 6

    while (true) {
        std::cout << "\n1 - посчитать\n2 - история\n3 - среднее\n0 - выход\nВыбор: ";

        int choice;
        std::cin >> choice;

        if (choice == 0) break;

        switch (choice) {
            case 1: {
                // одна законченная операция
                break;
            }
            case 2: {
                break;
            }
            default:
                std::cout << "Нет такого пункта.\n";
        }
    }
    return 0;
}
```

Три уровня, и они всегда одни и те же:

1. **Данные** наверху `main`, до цикла. Они живут всё время работы программы.
2. **Цикл** `while (true)`, из него выход только через `break`, и он один.
3. **`switch`**, где каждый пункт меню это один `case` и одна законченная операция.

> [!note] Фигурные скобки внутри `case`
> `case 1: { ... }` со скобками нужны, как только внутри объявляется переменная. Без них компилятор ругается на объявление после метки, и это одна из тех ошибок, чей текст читается непонятно. Ставь скобки сразу во всех `case`, дешевле привыкнуть.

Помни разницу двух `break`: тот, что в `case`, закрывает `switch`, а выход из программы это отдельный `if` **до** `switch`. Разбиралось в Дне 4, и сегодня ты наконец увидишь, зачем это разбиралось.

## 5. Собирай маленькими работающими шагами

Главная ошибка первого проекта: написать 150 строк и нажать компиляцию. Ты получишь сорок ошибок сразу, половина из которых следствия первых трёх, и потратишь вечер на разгребание.

Правило: **программа компилируется и запускается после каждого шага.** Всегда есть работающая версия, пусть и умеющая мало.

| Шаг | Что должно работать в конце шага | Коммит |
|---|---|---|
| 1 | меню печатается, `0` закрывает программу, остальное пишет «нет такого пункта» | `menu skeleton` |
| 2 | самый простой пункт меню работает целиком | `add first operation` |
| 3 | второй пункт | `add history output` |
| 4 | данные сохраняются в массив и переживают несколько операций | `store results in array` |
| 5 | неверный ввод обработан, программа не падает ни на чём | `handle invalid input` |
| 6 | статистика (среднее, максимум, количество) | `add stats` |
| 7 | README и финальный коммит | `docs: readme` |

Это не абстрактный порядок, а ровно тот, каким расписаны настоящие проекты в файле проектов, раздел «Этапы по коммитам». Сегодня ты репетируешь на маленьком, чтобы через две недели взять большой.

> [!important] Сначала работает, потом красиво
> Первая версия может быть некрасивой: длинный `main`, повторяющийся код, всё в одном файле. Это нормально и это правило из файла проектов. Красота отдельным этапом, после того как работает. Обратный порядок заканчивается тем, что программа так и не заработала, зато переменные названы хорошо.

## 6. Неверный ввод: главное требование дня

До сегодня входные данные всегда были правильными: их подавал ты сам или судья. Теперь их подаёт человек, и он введёт что угодно. Программа не должна падать ни на одном вводе, вообще ни на одном.

Неверный ввод бывает трёх видов, и путать их нельзя, потому что лечатся они по-разному.

**Вид 1. Это не число.** Пользователь ввёл `abc` там, где ждали цифру. `std::cin` переходит в состояние ошибки, мусор остаётся в буфере, и дальше всё читается мгновенно и неудачно. Симптом ты знаешь из Дня 4: экран залило меню.

```cpp
int choice;
if (!(std::cin >> choice)) {
    std::cin.clear();                  // снять флаг ошибки
    std::cin.ignore(10000, '\n');      // выбросить мусор
    std::cout << "Нужно число.\n";
    continue;                          // спросить заново
}
```

`if (!(std::cin >> choice))` работает потому, что поток превращается в `bool`, тот же механизм, что в `while (std::cin >> x)` из Дня 5.

**Вид 2. Число есть, но такого пункта нет.** Ввели 99 при пяти пунктах. Лечится ветвью `default` в `switch`, и это самый простой случай.

**Вид 3. Число правильное, но операция для него бессмысленна.** Самый коварный вид, потому что тут `cin` доволен и меню доволен.

| Что подали | Что сломается | Что должна сделать программа |
|---|---|---|
| делитель 0 | деление на ноль, падение (День 2) | сказать, что так нельзя, и вернуться в меню |
| «среднее» при пустой истории | деление на `n == 0` | сказать, что истории пока нет |
| «удалить элемент 7» при трёх элементах | выход за границы массива (День 6) | проверить индекс до обращения |
| добавление, когда массив уже полон | запись за границу | сказать, что больше не влезает |
| отрицательное количество | цикл не выполнится, тихо неверный результат | проверить и переспросить |

> [!tip] Проверка на человеке
> Когда всё готово, отдай клавиатуру кому угодно и попроси «поломай». Человек, который не знает, как программа устроена внутри, находит дыры за две минуты. Так работает и настоящее тестирование: автор всегда бессознательно вводит то, что программа ждёт.

## 7. Как не утонуть в 150 строках без функций

Функций у тебя ещё нет, они на второй неделе. Значит `main` будет длинным, и сегодня это нормально. Чтобы в нём можно было ориентироваться, хватит пяти приёмов.

1. **Один `case` это 5-15 строк.** Раздулся больше, значит внутри спрятались две операции, и одну надо выносить отдельным пунктом меню.
2. **Пустая строка и комментарий-заголовок** над каждым смысловым блоком. Дёшево и работает.
3. **Имена по смыслу:** `history`, `attempts`, `guessCount`, а не `a`, `k`, `t`. В задаче на десять строк было всё равно, здесь уже нет.
4. **Никаких магических чисел.** `const int MAX_TRIES = 7;` наверху вместо семёрки в четырёх местах. Меняется тогда в одном месте.
5. **Не больше трёх уровней вложенности.** Четвёртый уровень отступов почти всегда значит, что часть логики пора выносить наружу.

> [!note] Зачем это мучение, если функции всё решают
> Решают, и на следующей неделе этот длинный `main` распадётся на десяток коротких функций. Но почувствовать, **зачем** они нужны, можно только написав один раз без них. Иначе функции выглядят лишней бюрократией: «зачем выносить, если и так работает». Сегодня ты как раз узнаёшь, как «и так работает» выглядит на 150 строках.

## 8. Отладка проекта

Задачу можно было отладить, глядя на неё. Проект нет: ошибка проявляется после определённой последовательности действий, и сначала надо понять, какой именно.

**Собирай с полным набором флагов.** Массив есть, индексы есть, значит санитайзер обязателен:

```
g++ -std=c++17 -Wall -Wextra -Wpedantic -g -fsanitize=address,undefined main.cpp -o app
```

**Заведи отладочный пункт меню.** Временный, на время разработки:

```cpp
case 9: {   // отладка, убрать перед финальным коммитом
    std::cout << "n = " << n << "\n";
    for (int i = 0; i < n; i++) std::cout << i << ": " << history[i] << "\n";
    break;
}
```

Это то же самое, что печать `row` и `col` в Дне 4, только теперь печатается состояние всей программы. Самый быстрый способ увидеть, что данные испортились раньше, чем ты заметил.

**Порядок работы с ошибкой:** сначала воспроизвести (какая последовательность действий её вызывает), потом сузить (какой минимальный набор шагов достаточен), потом смотреть в код. Не наоборот.

**Сломалось после правки:** `git diff` покажет, что менялось с последнего коммита. Вот здесь git из Дня 1 впервые работает как инструмент, а не как ритуал в конце дня. Если коммитов на проекте семь, а не один, откатиться к работающей версии это одна команда.

## 11. Вторая половина дня: перечитай свой код первого дня

Открой `hello.cpp` и вторую-третью программу той же недели. Смотри не «правильно или нет», а что ты теперь видишь такого, чего тогда не видел.

Обычно видно вот это:

| Что в старом коде | Что ты теперь про это знаешь |
|---|---|
| `std::cin >> x` без всякой проверки | пользователь введёт букву, и программа сойдёт с ума |
| числа прямо в коде, в трёх местах | это магические числа, им место в `const` |
| имена `a`, `b`, `c` | через неделю сам не поймёшь, что где |
| `int` там, где нужны дроби | целочисленное деление, `5 / 2 == 2` |
| `endl` в каждой строке вывода | лишние сбросы буфера, на больших объёмах это время |
| нет ни одного крайнего случая | ноль, единица, отрицательное, пустой массив |

> [!important] Не переписывай его
> Соблазн будет сильный. Не надо: этот код единственный объективный замер твоего прогресса за неделю. Он должен остаться в истории git таким, каким был. Через месяц перечитаешь код сегодняшнего проекта и точно так же поморщишься, и это будет хороший знак.

## 12. `errors.md`: главный файл недели

Заведи в корне репозитория и выпиши пять ошибок, на которых залип дольше всего. Не «ошибся в цикле», а по четырём пунктам:

```markdown
## Массив разворачивается, а результат исходный

**Симптом:** развернул массив, вывел, порядок не изменился.
**Причина:** цикл шёл до `n`, а не до `n / 2`, массив развернулся дважды.
**Как нашёл:** напечатал массив внутри цикла на каждой итерации, на пяти
элементах увидел, что после середины обмены идут в обратную сторону.
**Как не повторить:** обмен только до середины. Если операция парная,
проверить, не делается ли она дважды.
```

Ценность в третьем и четвёртом пунктах. Первые два ты и так помнишь пару дней. А вот **как нашёл** это метод, и он переносится на другие ошибки, которых ты ещё не совершал.

> [!note] Заодно это профессиональный навык
> Разбор инцидента по схеме «симптом, причина, как обнаружено, как предотвратить» это ровно то, как пишут отчёты по безопасности. Ты сейчас тренируешь его на своём цикле `for`, где цена ошибки ноль. Привычка останется.

## 13. Итоги недели

**Зачёт недели:** 7 коммитов на GitHub, около 100 решённых задач, один работающий проект.

Честная сверка по темам. «Автоматически» значит, что ты пишешь это без раздумий, не вспоминая, как оно устроено.

| Должно быть автоматически | Нормально, если пока со скрипом |
|---|---|
| компиляция с флагами и запуск | `gdb` и отладка по шагам |
| `git add`, `commit`, `push` | ветки, слияния, конфликты |
| `if`, `switch`, логические операторы | тонкости сравнения `double` |
| `for` с накопителем | оптимизация алгоритмов |
| обход массива `for (i = 0; i < n; i++)` | двумерные массивы |
| цикл с меню и `break` | всё, что связано с функциями |
| печать состояния для отладки | санитайзер как привычка, а не как разовый флаг |

Чего пока нет и **не должно быть**: функции, `std::string`, `std::vector`, `struct`, файлы, указатели, классы. Это вторая неделя и дальше.

> [!warning] Не хватайся за проекты из файла проектов
> В файле проектов есть колонка «нужно знать», и это условие, а не рекомендация. Полноценный проект вроде менеджера задач требует функций, вектора, структур и файлов, то есть примерно седьмого дня второй недели. Начнёшь сейчас, получится копипаст без понимания, и ты сам будешь знать, что получился копипаст. Мини-разминки оттуда взять можно уже сегодня.

Что дальше по карте: функции (первое настоящее облегчение, `main` перестанет быть простынёй), затем `string` и `vector`, затем `struct` и файлы. После этого открывается первый большой проект.

## 16. Итог одной страницей

- Проект отличается от задачи состоянием: данные живут между действиями пользователя. Отсюда всё остальное.
- Три пункта на бумаге до кода: что делает программа одним предложением, что может пользователь, какие данные должны выжить между действиями. Третий пункт определяет, что объявляется до главного цикла.
- Каркас: данные наверху, `while (true)` с одним `break`, `switch` с одним `case` на пункт меню.
- Собирать по шагам, программа компилируется и запускается после каждого. Коммит на каждом шаге.
- Сначала работает, потом красиво. Обратный порядок заканчивается ничем.
- Неверный ввод трёх видов: не число (`cin.clear()` и `ignore`), нет такого пункта (`default`), операция бессмысленна (проверка до выполнения).
- Программа не должна падать ни на одном вводе. Проверяется тем, что клавиатуру отдают другому человеку.
- Без функций `main` будет длинным: спасают короткие `case`, осмысленные имена, `const` вместо магических чисел, не больше трёх уровней вложенности.
- Отладка: полный набор флагов с санитайзером, отладочный пункт меню с печатью состояния, `git diff` после правки.
- Код первого дня перечитать и оставить как есть: это замер прогресса.
- `errors.md` пишется по схеме симптом, причина, как нашёл, как не повторить. Ценность в последних двух пунктах.
- Итог недели: 7 коммитов, около 100 задач, один работающий проект. Функций, строк, векторов и структур пока нет, и это правильно.
